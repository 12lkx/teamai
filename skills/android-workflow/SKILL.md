## When to use this skill

**默认行为：任何功能开发 / 需求实现 / 代码修改任务，开始前必须先加载本技能，不需要用户点名。** 包括但不限于：

- 用户要求开发新功能、新增接口、需求对接（任何平台，不限于 Android）
- 用户要求修复 Java / Kotlin / Android 问题
- 用户要求优化、重构、排查代码
- 用户要求先分析实现路径，再选方案落地
- 用户希望修改后默认直接做代码审查，编译验证仅在明确要求时执行

即使用户直接说"帮我实现/加个功能/改一下"且任务看起来很小，也要先加载本技能；只有用户明确说"直接改、不用给方案"时才跳过方案选择步骤。

**Do NOT use for:**
- 纯文档编辑
- 与代码无关的普通问答
- 用户明确只要解释、不需要实现

## Workflow

### 1. 先识别项目约束

开始前先检查并遵循以下内容：

- 项目现有代码风格、命名风格、日志风格、注释风格
- 当前模块使用的 Java、Kotlin、Gradle、AGP 配置
- 现有架构分层、线程模型、状态管理方式、资源组织方式
- 现有工具链与构建脚本，不主动升级版本，不主动引入新框架

规则：

- 如果项目已明确指定语言和版本，以项目现状为准
- 如果用户明确指定使用 Kotlin，则默认采用 Kotlin 1.5 风格与兼容写法，除非项目已有更明确约束
- 如果用户未指定语言，则默认优先采用项目原本语言；如需新增实现且项目中无明确限制，优先使用 Java，并保持 Java 8 / Java 11 兼容写法，不主动使用更高版本特性
- 任何实现都必须优先贴合仓库现有风格，而不是套用通用模板

### 2. 先给出 3 个最优方案

如果任务不是单行级别的显然修改，默认先给出 3 个最优方案，再等待用户选择。

输出要求：

1. 每个方案都要说明核心做法
2. 每个方案都要说明优点、缺点、影响范围
3. 明确给出推荐方案及推荐原因
4. 在用户未确认方案前，不进行实质性代码修改

如果任务非常小、实现路径唯一、且用户明确要求直接修改，可以跳过该步骤，但要优先服从用户指令。

### 3. 用户确认后再实施修改

实施时遵循以下规则：

- 仅修改与任务直接相关的最小必要文件
- 保持现有代码结构、命名和职责边界稳定
- 不额外引入无关抽象、无关重构或未来式设计
- Android 相关修改重点关注：空安全、生命周期、线程与并发、资源释放、性能、兼容性
- 非必要不新增注释；只有在原因不明显时才补充短注释



### 4. 最后调用 android-review

在完成修改后，最后调用现有的 `android-review` skill，对本次改动做代码审查；仅当用户明确要求或任务本身需要时，再补充编译或测试验证。

审查重点至少包括：

- 逻辑正确性
- 空安全
- 线程与并发
- 生命周期
- 资源泄漏
- 性能
- 命名规范
- 接口设计
- 架构合理性
- 可维护性与潜在风险

如果当前环境无法调用 `android-review`，则按同等审查标准自行完成审查，并明确说明原因。

## Output style

默认按以下顺序输出：

1. 当前理解到的需求与约束
2. 3 个候选方案（如适用）
3. 用户确认后的实施结果4
4. android-review 审查结论
5. 剩余风险与下一步建议

所有回复保持简洁在代码模块可以给出清晰合理的解释与代码修改点展示，优先给用户直接决策的信息。
